= Bean Validation

Jakarta Bean Validation works by associating `ConstraintValidator` implementations with constraint annotations
and their target types. Since domain-primitives introduce new types, validators like `@Email` or `@Min` do
not work with them out of the box.

This generator creates `ConstraintValidator` implementations for every domain-primitive so that standard
Jakarta Bean Validation constraint annotations can be applied directly on domain-primitive fields.
The generated validators are registered via the `META-INF/services/jakarta.validation.ConstraintValidator`
service-loader mechanism and are therefore discovered automatically by any compliant Bean Validation provider
(Hibernate Validator, etc.).

NOTE: From a modeling perspective, external bean-val annotations provide less accurate semantics as it
means the object is created with a state that might be invalid. Nevertheless, in some cases it is necessary
to have these validators, like when OpenAPI generators map directly to the domain-types and the generator adds
validation annotations.

== Config Options

|===
|Property |Description

|_lazyval.beanvalidation.package_
|Specifies the package where the validator classes are generated to.
Overrides `lazyval.generators.basePackage`.

|===

== Supported Constraint Annotations

The validators that are generated depend on the wrapped type of each domain-primitive.

=== String-based domain-primitives

For domain-primitives that wrap `String`, the following validators are generated:

|===
|Constraint |Generated Validator

|`@Pattern` |`<Type>PatternValidator`
|`@Email` |`<Type>EmailValidator`
|===

=== Numeric domain-primitives

For domain-primitives that wrap a numeric type (`int`, `Integer`, `long`, `Long`, `short`, `Short`,
`byte`, `Byte`, `float`, `Float`, `double`, `Double`, `BigDecimal`, `BigInteger`), the following
validators are generated:

|===
|Constraint |Generated Validator

|`@Min` |`<Type>MinValidator`
|`@Max` |`<Type>MaxValidator`
|===

=== Temporal domain-primitives

For domain-primitives that wrap a temporal type (`LocalDate`, `LocalDateTime`, `LocalTime`,
`OffsetDateTime`, `OffsetTime`, `ZonedDateTime`, `Instant`, `Year`, `YearMonth`, `HijrahDate`,
`JapaneseDate`, `MinguoDate`, `ThaiBuddhistDate`), the following validators are generated:

|===
|Constraint |Generated Validator

|`@Past` |`<Type>PastValidator`
|`@Future` |`<Type>FutureValidator`
|`@PastOrPresent` |`<Type>PastOrPresentValidator`
|`@FutureOrPresent` |`<Type>FutureOrPresentValidator`
|===

Domain-primitives wrapping types that are not listed above will be skipped by this generator.

== Generated Files

For each domain-primitive, one or more `ConstraintValidator` implementations are generated. Every
generated validator follows the same pattern:

* It implements `ConstraintValidator<AnnotationType, DomainPrimitiveType>`.
* `null` values are considered valid (returns `true`), consistent with the Bean Validation specification.
* It delegates to the inner value of the domain-primitive for the actual validation logic.

Additionally a `META-INF/services/jakarta.validation.ConstraintValidator` service-loader file is
generated that lists all validator classes, so they are automatically discovered at runtime.

=== String example

Given a `String`-based domain-primitive `Isbn`:

[tabs]
====
Java::
+
[source,java]
----
public class IsbnPatternValidator implements ConstraintValidator<Pattern, Isbn> {
  private String regex;

  @Override
  public void initialize(Pattern constraintAnnotation) {
    this.regex = constraintAnnotation.regexp();
  }

  @Override
  public boolean isValid(Isbn value, ConstraintValidatorContext context) {
    if (value == null) {
      return true;
    }
    return value.value().matches(regex);
  }
}
----

Kotlin::
+
[source,kotlin]
----
public class IsbnPatternValidator : ConstraintValidator<Pattern, Isbn> {
  private var regex: String = ""

  override fun initialize(constraintAnnotation: Pattern) {
    this.regex = constraintAnnotation.regexp
  }

  override fun isValid(value: Isbn?, context: ConstraintValidatorContext): Boolean {
    if (value == null) {
      return true
    }
    return value.value.matches(Regex(regex))
  }
}
----
====

=== Numeric example

Given an `int`-based domain-primitive `Quantity`:

[tabs]
====
Java::
+
[source,java]
----
public class QuantityMinValidator implements ConstraintValidator<Min, Quantity> {
  private long min;

  @Override
  public void initialize(Min constraintAnnotation) {
    this.min = constraintAnnotation.value();
  }

  @Override
  public boolean isValid(Quantity value, ConstraintValidatorContext context) {
    if (value == null) {
      return true;
    }
    return value.value() >= min;
  }
}
----

Kotlin::
+
[source,kotlin]
----
public class QuantityMinValidator : ConstraintValidator<Min, Quantity> {
  private var min: Long = 0

  override fun initialize(constraintAnnotation: Min) {
    this.min = constraintAnnotation.value
  }

  override fun isValid(value: Quantity?, context: ConstraintValidatorContext): Boolean {
    if (value == null) {
      return true
    }
    return value.value >= min
  }
}
----
====

=== Temporal example

Given a `LocalDate`-based domain-primitive `OrderDate`:

[tabs]
====
Java::
+
[source,java]
----
public class OrderDatePastValidator implements ConstraintValidator<Past, OrderDate> {
  @Override
  public boolean isValid(OrderDate value, ConstraintValidatorContext context) {
    if (value == null) {
      return true;
    }
    return value.date().isBefore(java.time.LocalDate.now());
  }
}
----

Kotlin::
+
[source,kotlin]
----
public class OrderDatePastValidator : ConstraintValidator<Past, OrderDate> {
  override fun isValid(value: OrderDate?, context: ConstraintValidatorContext): Boolean {
    if (value == null) {
      return true
    }
    return value.value.isBefore(java.time.LocalDate.now())
  }
}
----

== Usage

Once the validators are generated, standard Bean Validation annotations work directly on domain-primitive
fields:

[tabs]
====
Java::
+
[source,java]
----
public record CreateOrderRequest(
    @Pattern(regexp = "^[0-9]{13}$") Isbn isbn,
    @Min(1) Quantity quantity,
    @PastOrPresent OrderDate orderDate
) {}
----

Kotlin::
+
[source,kotlin]
----
data class CreateOrderRequest(
    @field:Pattern(regexp = "^[0-9]{13}$") val isbn: Isbn,
    @field:Min(1) val quantity: Quantity,
    @field:PastOrPresent val orderDate: OrderDate
)
----
====

No additional configuration is required — the validators are automatically discovered by the Bean
Validation provider through the service-loader mechanism.
