= Bean Validation

NOTE: From a modeling perspective, external bean-val annotations provide less accurate semantics, as it
means the object is created with a state that might be invalid. Nevertheless, in some cases it is necessary
to have these validators. A primary use-case is legacy or migration projects, where domain-primitives cannot
(yet) enforce their invariants during construction and after-the-fact validation is still needed. Another
use-case is when OpenAPI generators map directly to the domain-types and add validation annotations.

Jakarta Bean Validation works by associating `ConstraintValidator` implementations with constraint annotations
and their target types. Since domain-primitives introduce new types, validators like `@Email` or `@Min` do
not work with them out of the box.

This generator creates a `ValueExtractor` for each domain-primitive. A value extractor tells the Bean
Validation provider how to unwrap the inner value of a domain-primitive so that all the provider's
built-in constraint validators work transparently.

The generated extractor is registered via the
`META-INF/services/jakarta.validation.valueextraction.ValueExtractor` service-loader mechanism and is
therefore discovered automatically by any compliant Bean Validation provider (like Hibernate Validator).

== Generated Files

For each domain-primitive a `<Name>ValueExtractor` is generated and added to the also generated
`META-INF/services/jakarta.validation.valueextraction.ValueExtractor` service-loader file so the
implementations are discovered by the provider at runtime.

[tabs]
====
Java::
+
[source,java]
----
@UnwrapByDefault
public class EMailValueExtractor implements ValueExtractor<@ExtractedValue(type = String.class) EMail> {
  @Override
  public void extractValues(EMail originalValue, ValueExtractor.ValueReceiver receiver) {
    if (originalValue == null) {
      receiver.value(null, null);
      return;
    }
    receiver.value(null, originalValue.value());
  }
}
----

Kotlin::
+
[source,kotlin]
----
@UnwrapByDefault
public class EMailValueExtractor : EMailValueExtractorBase() {
  override fun extractValues(originalValue: EMail?, `receiver`: ValueExtractor.ValueReceiver) {
    if (originalValue == null) {
      receiver.value(null, null)
      return
    }
    receiver.value(null, originalValue.value)
  }
}
----
+
IMPORTANT: For Kotlin, a second Java source file is generated — see <<why-java,Why a Java class is required>>.
+
[source,java]
----
public abstract class EMailValueExtractorBase implements ValueExtractor<@ExtractedValue(type = String.class) EMail> {
}
----
====

== Supported Wrapped Types

The extractor is generated for every domain-primitive regardless of its wrapped type. The constraint
annotations that become available after generation depend on what the Bean Validation provider
supports for the inner type:

|===
|Wrapped type |Example constraints unlocked

|`String`
|`@Pattern`, `@Email`, `@NotBlank`, `@Size`

|Numeric (`int`, `Integer`, `long`, `Long`, `BigDecimal`, …)
|`@Min`, `@Max`, `@Positive`, `@Negative`, `@Digits`

|Temporal (`LocalDate`, `Instant`, `ZonedDateTime`, …)
|`@Past`, `@Future`, `@PastOrPresent`, `@FutureOrPresent`

|===

Domain-primitives wrapping other types will still get an extractor; available constraints depend
on what the provider registers for that type.

== Usage

Once the extractors are generated, standard Bean Validation annotations work directly on
domain-primitive fields:

[tabs]
====
Java::
+
[source,java]
----
public record CreateOrderRequest(
    @Pattern(regexp = "^[0-9]{13}$") Isbn isbn,
    @Min(1) Quantity quantity,
    @PastOrPresent OrderDate orderDate,
    @Email EMail email
) {}
----

Kotlin::
+
[source,kotlin]
----
data class CreateOrderRequest(
    @field:Pattern(regexp = "^[0-9]{13}$\") val isbn: Isbn,
    @field:Min(1) val quantity: Quantity,
    @field:PastOrPresent val orderDate: OrderDate,
    @field:Email val email: EMail
)
----
====

No additional configuration is required — the extractors are automatically discovered by the Bean
Validation provider through the service-loader mechanism.

== NonNull

Domain-primitives are expected to enforce non-null of their inner value at construction
(a factory or constructor guard rejects `null`). `@NotNull` on a wrapper-typed field is
therefore never about the inner value — it can only be a statement about the *reference*.

Because the generated extractor carries `@UnwrapByDefault`, every constraint on the field,
including `@NotNull`, is redirected to the extracted value. When the wrapper reference itself
is `null` the Bean Validation provider skips extraction entirely, so `@NotNull` silently
matches nothing.

To assert non-null of the reference, opt the `@NotNull` constraint out of unwrapping with
`payload = Unwrapping.Skip.class`. Other constraints stay unwrapped:

[tabs]
====
Java::
+
[source,java]
----
public record CreateOrderRequest(
    @NotNull(payload = Unwrapping.Skip.class)
    @Pattern(regexp = "^[0-9]{13}$") Isbn isbn
) {}
----

Kotlin::
+
[source,kotlin]
----
data class CreateOrderRequest(
    @field:NotNull(payload = [Unwrapping.Skip::class])
    @field:Pattern(regexp = "^[0-9]{13}$")
    val isbn: Isbn
)
----
====


[#why-java]
== Kotlin: Why a Java Class is Required

The Java annotation processor generates a single `.java` file and requires no further explanation.
For the Kotlin KSP processor, however, two files are needed because of a Kotlin compiler limitation.

The Bean Validation specification requires that a `ValueExtractor` implementation declares
`@ExtractedValue` as a type-use annotation on its generic supertype argument:

[source,java]
----
implements ValueExtractor<@ExtractedValue(type = LocalDate.class) OrderDate>
----

Compliant providers like Hibernate Validator discover this annotation by inspecting
`Class.getAnnotatedInterfaces()` at runtime.
This method reads `RuntimeVisibleTypeAnnotations` — a JVM bytecode attribute that holds
type-level annotations in a location-aware form.

The Kotlin compiler does *not* emit `RuntimeVisibleTypeAnnotations` for type-use annotations placed
on generic supertype arguments (https://youtrack.jetbrains.com/issue/KT-19289[KT-19289]).
The annotation is stored only in Kotlin's own `@Metadata`, which the Bean Validation provider
does not consult.

To work around this, the KSP generator splits the extractor into two files:

1. **`OrderDateValueExtractorBase.java`** — an abstract Java class compiled by `javac`.
`javac` correctly emits `RuntimeVisibleTypeAnnotations`, so the provider's reflection-based
discovery works.
2. **`OrderDateValueExtractor.kt`** — an idiomatic Kotlin class that extends the Java base and
provides the implementation.

This split is an internal implementation detail of the generator.
From a user perspective nothing changes: the extractor is auto-discovered, and constraint
annotations work on domain-primitives just as they do for the Java variant.
