= Testkit

The Lazyval testkit runs a real compiler toolchain against a temporary project you describe with a `Scenario`. It returns a typed `Testresult` you can compare with framework-native assertions; no custom matchers required.

== Quick start

[source, java]
----
var tmpDir = Path.of(System.getProperty("java.io.tmpdir")); // <1>
var scenario = Scenario.Java.ofSingle("scenarios/java/MyTestLazyval.java") // <2>
    .withDependencies(
            new Dependency("some.groupId", "some.artifactId", "1.0.0")); // <3>
var result = Testkit.java().run(tmpDir, scenario); // <4>
----
<1> Working directory for generated sources and compiled classes. In practice, use your framework's temporary-directory facility (Spock `@TempDir`, JUnit `@TempDir`, Kotest `tempdir()`).
<2> Points at classpath-relative source files — typically under `src/test/resources`.
<3> The compile-classpath dependency the generator requires. Without it, Lazyval will not trigger generation for that SPI.
<4> Runs the scenario and returns a `Testresult` for direct comparison.

NOTE: when dealing with the `Scenario` API as shown in the previous example, you are actually dealing with a `ScenarioFactory` (builder pattern).
The testkit just provides a convenience method which handles the call to `build()`. The `Scenario` itself is immutable when passed to the toolchain.

== Choosing a toolchain

`Testkit.java()`:: Runs `javac` with Lazyval's annotation processor. Accepts `Scenario.Java`, returns `Testresult.Java`.

`Testkit.kotlin()`:: Runs `KSP2` with Lazyvals ksp processor followed by `kotlinc`, and in case Java code is emitted also `javac`.
Accepts `Scenario.Kotlin`, returns `Testresult.Kotlin`. In contrast to javac, KSP2 is not a Kotlin compiler plugin and
runs in a separate process before compilation — so the testkit invokes the compiler afterward to verify the generated code is valid.

Both factories throw `IllegalStateException` if the respective Lazyval processor is missing from the test classpath.

== Defining a scenario

A `Scenario` is the toolchain-typed description of what gets compiled. Each variant — `Scenario.Java` and `Scenario.Kotlin` — carries a `Descriptor` with source files, optional classpath dependencies, and optional processor options.

=== Predefined scenarios

The testkit ships a collection of valid scenarios for both Java and Kotlin so SPI providers don't have to invent input every time. Each covers a distinct Lazyval-relevant shape:

|===
|Scenario |What makes it interesting

|`isbn()`
|Class with a bean-convention getter (`getValue()`).

|`quantity()`
|Record / data-class wrapping a primitive (`int`) — exercises boxing in generators that need a reference type.

|`orderDate()`
|Record / data-class wrapping a non-primitive reference (`LocalDate`).

|`ids()`
|Sealed interface holding a nested record `ProductId` — inner-type handling, plus multiple factories of which only `of(String)` is relevant to Lazyval.

|`nullableQuantity()` _(Kotlin only)_
|Factory that can return `null` — exercises nullability propagation.
|===

IMPORTANT: Predefined scenarios still need the generator's required `Dependency`. Without it, Lazyval skips generation for that SPI by design.

=== `combined()` vs `all()`

`Scenario.Java.combined()`:: A *single* scenario-factory bundling every predefined source. One compilation, one assertion. Best when a generator emits one aggregate artifact (e.g. `LazyvalMapper.java`, `LazyvalCassandraCodecs.java`) or when verifying exact file contents via xref:testkit-approvals.adoc[approval testing]. Typically faster because the compiler boots once — prefer it where it fits.

`Scenario.Java.all()`:: A *list* of scenario-factories, one per predefined source. Use with your test framework's data-driven runner (Spock `where:`, Kotest `withData`) when you want per-scenario diagnostics or your generator emits a separate file per input.

=== Custom scenarios

For inputs the predefined set doesn't cover, build a scenario from arbitrary classpath resources:

[source, java]
----
var scenario = Scenario.Java.of("custom-multi-source",
        "scenarios/java/Quantity.java",
        "scenarios/cassandracodecs/ValidCassandraCodec.java")
    .withDependencies(myDependency)
    .withOption("lazyval.cassandra.codecs", "scenarios.cassandracodecs.ValidCassandraCodec");
----

The first argument is a display name used in test reports; subsequent arguments are classpath-relative source paths. `withOption(key, value)` feeds processor options the same way `-A<key>=<value>` would on the compiler command line.

=== Data-driven runs

See the xref:spi:testkit-spock.adoc[Spock] or xref:spi:testkit-kotest.adoc[Kotest] example for a data-driven setup that fans out over the predefined scenarios.

== Verifying results

`Testresult.Java` and `Testresult.Kotlin` are sealed interfaces enumerating every possible outcome:

|===
|Variant |Meaning

|`Success(generatedFiles)`
|Compilation succeeded, the listed files were produced, no warnings.

|`SuccessWithWarnings(generatedFiles, warnings)`
|Compilation succeeded but the listed warnings were emitted.

|`NothingGenerated`
|Compilation succeeded but no generator was active — typically because the required classpath was absent.

|`Failure(errors)`
|Compilation failed; the listed compiler errors were observed.

|`Approved(generatedFiles, warnings)`
|Strict-closed-set verdict from xref:testkit-approvals.adoc[approval testing]: every approval matched and no extra files were produced.

|`ApprovalMismatch(failures)`
|Strict-closed-set verdict from approvals failed. `toString()` renders a per-failure description, including the unified diff for content failures.
|===

Because results are records, framework-native equality is enough:

[tabs]
====
JUnit::
+
[source, java]
----
assertEquals(new Testresult.Java.Success("LazyvalMapper.java"), result);
----

Spock::
+
[source, groovy]
----
result == new Testresult.Java.Success("LazyvalMapper.java")
----

Kotest::
+
[source, kotlin]
----
result shouldEqual Testresult.Kotlin.Success("LazyvalMapper.java")
----
====

NOTE: The testkit API uses *Eclipse Collections* `ImmutableList` — which provides stronger guarantees than `Collections.unmodifiableList`.
For convenience, every constructor/factory also has a `List<String>` / varargs overload so call-sites can stay in the stdlib idiom (like Groovy list literal).

== Approval testing

Comparing file names is enough for simple cases. However, when the *exact content* of the produced file matters, approval testing pairs each expected artifact with a reference content and asserts the generator produced exactly that, *nothing more, nothing less*.

The same `run(...)` method accepts approvals as the final argument:

[source, java]
----
var result = Testkit.java().run(tmpDir, scenario, approvals);
assertEquals(Testresult.Java.Approved.of(approvals), result);
----

See xref:testkit-approvals.adoc[Approval Testing] for the full flow: variants, factories, strict closed-set semantics, diff tolerances, failure diagnostics, and how to refresh approvals after intentional changes.

== Configuration

Runtime behavior is controlled via JVM system properties and environment variables.

=== System properties

|===
|Property |Default |Description

|`lazyval.testkit.maven-repo`
|`<user-home>/.m2/repository`
|Absolute path to the folder where the testkit caches downloaded dependencies.

|`lazyval.testkit.maven-mirror`
|`https://repo1.maven.org/maven2/`
|Base URL of the Maven repository or mirror. Must expose the `maven2/` path so dependencies resolve as `<mirror>/<groupId>/<artifactId>/<version>/…`.

|===

CAUTION: The testkit mimics Maven for downloading and caching dependencies, but it does not read Maven-specific configuration files (`settings.xml`, `pom.xml`). If your environment blocks Maven Central or uses an internal registry (Nexus, Artifactory), override the defaults above.

=== Environment variables

|===
|Variable |Description

|`LAZYVAL_TESTKIT_MIRROR_USERNAME` +
`LAZYVAL_TESTKIT_MIRROR_PASSWORD`
|Basic-Auth credentials for the mirror. Required when the repository server does not allow anonymous access.

|===

== Logging

The testkit captures all output from the underlying toolchains and forwards it to SLF4J. To see anything, the test classpath must provide an SLF4J implementation (e.g. `slf4j-simple`); the testkit itself depends only on `slf4j-api`.
