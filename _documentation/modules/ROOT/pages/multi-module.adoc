= Multi-Module Support

This section describes support for more complex builds like a Modulith, Kotlin Multiplatform, or just sharing some
domain primitives between multiple Microservices.

In general, annotation processors are only concerned with the current compilation-unit, which means when searching for
annotated symbols, they only see source code within the current module. Luckily, they can also inspect classes from
the classpath, which is how Lazyval provides a way to support multi-module setups.

== Declaring external value types

Add the `@LazyvalConfiguration` annotation to your module and list the external value types via `externalTypes`.
Listed types behave as if they had been annotated with `@LazyValue` themselves, even though they live in another
module on the classpath.

NOTE: a dedicated annotation is needed instead of a processor option, because in case no annotation is present
in the current compilation-unit, when all types come from a shared module, the processor would not be triggered at all.

[tabs]
====
Java::
+
Place the annotation on a single `package-info.java` per compilation unit (typically the top-level package of the
module).
+
.com/acme/a/package-info.java
[source,java]
----
@LazyvalConfiguration(externalTypes = {EMail.class, AcmeId.class})
package com.acme.a;

import com.qualityminds.lazyval.LazyvalConfiguration;
import com.acme.shared.EMail;
import com.acme.shared.AcmeId;
----

Kotlin::
+
KSP does not expose annotations on `package-info.java`, and Kotlin has no package-level annotation site. Place the
annotation on a single, dedicated marker object instead.
+
.LazyvalConfig.kt
[source,kotlin]
----
@LazyvalConfiguration(externalTypes = [EMail::class, AcmeId::class])
object LazyvalConfig
----
====

Only one `@LazyvalConfiguration` per compilation unit is allowed; the processor reports a compile error otherwise.
Types listed in `externalTypes` that belong to the current compilation unit are also rejected — annotate them with
`@LazyValue` directly in that case.

A module that has no `@LazyValue`-annotated types of its own can still drive generation purely from
`externalTypes`, which is the common setup for a service module that only consumes a shared domain.

== Sample structure

.sample module structure
----
├── shared/
│   ├── com.acme.shared.EMail
│   └── com.acme.shared.AcmeId
├── service-a/
│   ├── com.acme.a.Foo
│   └── com.acme.a.package-info       // @LazyvalConfiguration(externalTypes = {EMail.class, AcmeId.class})
└── service-b/
    ├── com.acme.b.Bar
    └── com.acme.b.package-info       // @LazyvalConfiguration(externalTypes = {AcmeId.class})
----

Here `shared` only defines domain-primitives without any dependency to Lazyval at all (the shared types need no
`@LazyValue` annotation at all), while `service-a` and `service-b` are properly configured with the processor
and each carries its own `@LazyvalConfiguration` declaring which shared types to process.
