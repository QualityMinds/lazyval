= Rules

Everything Lazyval requires of a `@LazyValue`-annotated type, in one place. The getting-started pages
(xref:java.adoc[Java], xref:kotlin.adoc[Kotlin]) show what a domain primitive looks like; this page is the
rulebook behind those examples.

Every rule here is checked at compile time. A violation is a compile error naming the element that has
to change, rather than something you find out about from the generated sources later. The two
exceptions are marked as warnings below: they are advice about immutability, not requirements.

[#shape]
== Shape

[tabs]
====
Java::
+
A `record` or a `class`. An `abstract` class is rejected — there is nothing to instantiate.
+
A non-`final` class is accepted with a warning: a domain-primitive that can be subclassed is no longer a
value, but the decision is yours.

Kotlin::
+
A `class` or a `data class`. An `abstract` class is rejected, and so is a `value class`.
+
An `open` class is accepted with a warning, for the same reason as in Java.
+
`value class` is unsupported by design rather than by omission — see the
xref:kotlin.adoc[rationale on the Kotlin page].
====

[#payload]
== Exactly one payload

A domain-primitive wraps exactly one thing. Lazyval requires exactly one non-transient instance
field (Java) or property (Kotlin), and rejects a type that has none or more than one.

Derived state does not count against that rule, but it has to be declared as such, because from the
outside a cached computation looks exactly like a second payload:

[tabs]
====
Java::
+
Mark derived fields `transient`.

Kotlin::
+
Mark derived properties `@kotlin.jvm.Transient`.
====

Since the `transient` keyword only carries meaning for types implementing `Serializable`, static
analysis tends to flag it everywhere else. Lazyval therefore accepts these annotations as equivalent,
on either the field/property or its accessor (in Kotlin: `@get:Transient`):

* `jakarta.persistence.Transient`
* `org.springframework.data.annotation.Transient`

These two are supported because of their wide usage. On any other stack, use the plain `transient`
keyword (`@kotlin.jvm.Transient` in Kotlin) or map the domain-primitive to its wrapped value in a
dedicated persistence model.

For records, place the annotation directly on the derived record component. Since the canonical
constructor then takes more than the payload, provide a single-argument constructor or a factory-method,
so generated code can reconstruct the value from the payload alone — see <<factory>>.

Additional constructors, accessors, and convenience factories with other signatures are allowed and don't
break the rules.

[#visibility]
== Visibility

Generated code is emitted into its own package. Anything the generated code has to touch at runtime therefore has
to be reachable from outside the domain-primitive's package — which in practice means `public`. Part of the
generated output is Java even for a Kotlin project, which is what makes this stricter than it first
looks.

[tabs]
====
Java::
+
The *accessor* has to be `public`. The field itself is free to stay `private`, which is the idiomatic
shape and the one the xref:java.adoc#usage[Java examples] use.
+
A field with no public accessor is invisible to Lazyval, so it needs no `transient` to be excluded. The
derived field in the `Birthdate` example does need it, precisely because its accessor is public.

Kotlin::
+
The *property* has to be `public`; `private`, `protected` and `internal` are each rejected with an
error reported on the property.
+
As in Java, a property generated code cannot reach is invisible rather than illegal: an extra
`private` or `internal` helper property alongside the payload neither counts towards the one-payload
rule nor needs a `@Transient`. Only when _no_ property is readable does each one get an error.
+
`internal` is the surprising one, because it _looks_ like it should work: it is visible to the whole
module, and the generated sources are part of that module. What breaks it is the JVM name — Kotlin
mangles an internal property's getter to `getValue$module`, and the Java half of Lazyval's output then
finds no `getValue()` to call.
+
This applies to the property, not to the type: an `internal` class is fine, because class names are
not mangled.
+
If you would rather not widen the property, expose a `public` accessor function instead. Lazyval calls
that function and leaves the property alone — the Kotlin counterpart of the Java rule in the other tab:
+
[source,kotlin]
----
@LazyValue
class Reference(private val value: String) {

    fun value(): String = value
}
----
====

The same bar applies to the way back in — the constructor or factory method Lazyval calls to rebuild
the value from its payload. That half is covered under <<factory>>.

It applies to the domain-primitive itself as well, since generated code has to name the type before it
can read or rebuild it. A Java type that is not `public`, and a Kotlin type that is neither `public`
nor `internal`, are rejected for the same reason a hidden accessor is. An `internal` Kotlin class
stays fine, as above, which is why the Kotlin error names both ways out. Types pulled in from another
module are held to the same bar — see <<external>>.

[#immutability]
== Immutability

Advice, not a rule. Lazyval warns when the class is not `final` (`open` in Kotlin) or the payload is
not `final` (`var` in Kotlin), and generates anyway.

[#factory]
== Factory methods

Lazyval reconstructs a value either through a factory method or through the constructor. A factory
method is one that returns the domain-primitive and takes a single parameter of the payload type. Its name is
free — `of`, `parse`, `valueOf`, anything. In Java it has to be `static`; in Kotlin it is a
companion-object function.

At most one method may match that signature. With several, Lazyval cannot tell which one is meant to
reconstruct the value and reports an error listing the candidates. With none, the constructor is used
instead, and it then has to take the payload and nothing else.

Whichever of the two carries the value back has to be reachable from the generated package, for the
reason given under <<visibility>>. Being `static` does not make a `private` factory a way in, so a
type with a `private` constructor needs a `public` factory rather than merely any factory. The error
lands on whichever of the two Lazyval would have called.

NOTE: In Kotlin the two part ways on `internal`. An `internal` factory function is rejected, because
Kotlin mangles its JVM name and the Java half of the generated output has no unmangled name to call —
the same mechanism that rules out an `internal` property under <<visibility>>. An `internal`
constructor is accepted, because constructors are not name-mangled, just as an `internal` class is.

In Kotlin, nullability is ignored when matching: a `fun ofNullable(value: String?): Isbn?` counts as a
factory for a `String` payload, and counts towards the at-most-one limit alongside a
`fun of(value: String): Isbn`. A constructor parameter is matched the same way.

[#payload-type]
== Payload type

[tabs]
====
Java::
+
Any type the active generators can handle. See xref:generators:index.adoc[Generators] for what each
one supports, and for how to plug in a converter for a type it does not.

Kotlin::
+
Must not be nullable. `String?` is rejected — a domain-primitive whose payload may be absent is not a value.
+
Beyond that, the same generator-side considerations as for Java apply.
====

[#external]
== Shared types from other modules

Types pulled in via `@LazyvalConfiguration(externalTypes = ...)` follow every rule above, read from the
classpath rather than from source. Since the consuming module is a different compilation unit, the
reachability bar applies to the whole chain: the type, its factory method or constructor, and the
accessor for the payload.

For Kotlin that additionally rules out `internal` *members* for a second, simpler reason than the name
mangling above — `internal` is scoped to the module that declares it, and no configuration widens that
scope. The type itself needs no rule of its own here: an `internal` class in another module cannot be
named in `externalTypes` to begin with.
