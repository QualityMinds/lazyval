= Kotlin Support via KSP2

For Kotlin, the original Java Annotation Processor was migrated to KSP2 (Kotlin Symbol Processing) to make use of
the `@LazyValue` annotation on Kotlin classes and data-classes.

Kotlin's `value class` looks like the natural fit for domain primitives, but on the JVM it comes with caveats.
Because the wrapper is inlined, reflection- and bytecode-based tooling (JPA/Hibernate, Spring Data, MapStruct)
only ever sees the underlying `Int` or `String` and has nothing to attach a converter to; functions taking a
value class also get mangled JVM names that Java callers cannot invoke.

Lazyval takes the opposite route: keep an ordinary class or data class — a shape every framework already
understands — and let the processor generate the integration code you would otherwise write by hand. You trade
the runtime unboxing of `value class` for a wrapper the ecosystem can actually work with.

That is about the domain-primitive. A `value class` as the *payload* of one is a separate question with
the opposite answer: it is supported, and Lazyval unwraps it — see
xref:rules.adoc#value-class[Value class payloads] for what that costs and where it stops.

A value type may carry derived properties that are computed from the stored payload (here `asLocalDate` from `value`).
Lazyval validates that exactly one non-transient property is the stored payload, so any derived property must
be marked `@kotlin.jvm.Transient` to keep it out of the validation.

Note that the payload is read through the property's getter, which is why `value` is `public` in all three
examples. `internal` does not qualify either, even though the generated sources live in the same module.

TIP: xref:rules.adoc[Rules] is the complete reference: shape, payload,
visibility — including why `internal` is rejected and how to keep a
property non-public anyway — factory methods, and what `transient` accepts besides the annotation.
