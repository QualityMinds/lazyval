= Lazyval: Compile-Time Code Generator for Domain Primitives in Java & Kotlin

== Motivation

Good domain modeling means using dedicated types instead of raw primitives.
A `Quantity`, an `Isbn`, or an `EmailAddress` each carry their own invariants and make invalid states unrepresentable.
The book https://www.manning.com/books/secure-by-design[Secure by Design] calls these _"Domain Primitives"_.
Another inspiration for this project was Scala's https://www.scala-lang.org/api/current/scala/AnyVal.html[AnyVal].

=== The Problem

In practice, every domain primitive you introduce comes with a tax: you need to write a JPA `AttributeConverter` so the ORM can persist it, a Jackson de/serializer so it travels correctly/efficient over the network, a MapStruct mapping so it converts between layers, and so on.
This boilerplate adds up quickly and discourages teams from modeling their domain properly — they fall back to raw `String` and `int` fields instead.

=== How Lazyval Solves It

Lazyval is a *compile-time code generator* that eliminates this boilerplate — with first-class support for both *Java* (annotation processor) and *Kotlin* (KSP2).
Annotate your type with `@LazyValue` (or configure shared types),
and Lazyval generates the necessary integration code during compilation — no runtime dependency, no marker interfaces, no glue code.

It is also smart about it:

* **Classpath detection** — only generates code for frameworks that are actually on your classpath. Add JPA? Converters appear. Remove it? They're gone.
* **Convention-free** — factory methods can be named arbitrarily; Lazyval infers the right one from the type signature.
* **Proper feedback** — warnings and errors are reported during compilation, not at runtime.

In a possible future where Java value types are fully supported by the ecosystem (meaning you can use a value type in a JPA entity without hassle), this project may no longer be needed.

== Design Goals

This section describes the key design goals of this project.

* Generate only source-code: no bytecode manipulation.

* Never require any runtime-dependency: all annotations are erased at compile-time.

* Narrow scope: supports only single-value domain primitives.

* Easy to extend and test.

* Eat your own dogfood: stock generators use SPI & Testkit.

Those goals yield some interesting properties from an end-user perspective. Most notably, no dependency on the project
and its maintainer when a new generator is needed, an existing generator has a bug or CVE, or you don't like the project
anymore and want to remove it from your codebase.


|===
|Problem |Solution

|Dont like it
|Copy & Own generated sources. Delete Lazyval. See you later.

|CVE / Bug in a generated file (hotfix needed asap)
|Copy & Own relevant file, disable flawed generator via id, fix the bug locally. Report the issue and wait for a fix.

|CVE / Bug / Missing Feature in existing generator
|Copy the existing generator source as a custom generator module and supersede the existing one. Apply a fix and use Testkit to verify. Add your custom generator to the annotation-processor path. Report the issue.

|New generator needed
|Use SPI to create a custom generator-module and verify it via Testkit.
Report a feature request and ideally supply your solution. PRs must cover
Kotlin & Java if applicable.

|Bug in core processor handling or domain-primitive rules.
|Report the issue.
|===

== Global Configuration Options

|===
|Property |Description

|_lazyval.generators.basePackage_
|When this option is set with the applications' base package, the generators use sensible defaults where the generated artifacts should be located (following hexagonal architecture guidelines). See specific generator about defaults and how to override.
In case no basePackage nor generator-specific override is provided, the package of the first domain-primitive is used as
fallback (custom generators might choose a different strategy).

|_lazyval.generators.disable_
|Comma separated List of Generator-IDs that should not generate output despite being found on the classpath.
Active Generator-IDs are printed to the console during compilation.

|_lazyval.generators.supersede_
|Allows disabling the xref:spi:index.adoc#superseding-other-generators[supersede-feature] for generators. Defaults to 'true'.

|===

NOTE: External value types from other modules are declared via the `@LazyvalConfiguration` annotation rather than a
processor option. See xref:multi-module.adoc[Multi-Module Support].

For generator-specific options, see the Generators section.
